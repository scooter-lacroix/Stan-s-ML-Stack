# v0.3.1 Detection / Managed-Python / Wiring — Source-Only Verification Report

**Method:** Direct source inspection only. No tests, git history, or teammate
assertions used as evidence. PCI-ID claims cross-checked against
`/usr/share/hwdata/pci.ids` and the authoritative ROCm GPU-arch spec
(`rocm.docs.amd.com/en/latest/reference/gpu-arch-specs.html`). Live sysfs on the
review box (`/sys/class/drm`) used to validate detection.

**Crate root:** `rusty-stack/src/`

**Headline finding (Critical):** The RDNA4 PCI-ID→gfx and marketing-name→gfx
mappings are **inverted** in *all four* mapping tables. Every RX 9070-class card
(Navi 48, the most common RDNA4 dGPU) is detected as `gfx1200` when it is
actually `gfx1201`; every RX 9060-class card (Navi 44) is detected as `gfx1201`
when it is `gfx1200`. This directly violates the foundational requirement that
detection "correctly identify … their gfx architectures." The unit tests
enshrine the wrong values, which is exactly why tests are not permissible
evidence here.

**Second structural finding (High):** The v0.3.1 permanent-env arm builds a
`PermanentEnvConfig` (precise per-variant HSA via `GpuArchInfo::from_arch`,
detector-derived device list, resolved python) that is **never written to
`.mlstack_env`**. The writer method `generate_env_file_content` is referenced
only from `#[cfg(test)]` code. The file that is actually produced comes from a
separate, older path (`installer.rs::ensure_mlstack_env`) that uses the *coarse*
`hsa_override_from_gpu_arch` (so `gfx1101`→`11.0.0`, not the precise `11.0.1`)
and sets `python_bin` independently. The arm's careful derivation is effectively
dead.

## PART A — v0.3.1 install hotfix

### A1. ROCm Arch install no longer triggers a full system upgrade — **MET**

- `installers/components/rocm.rs::pacman_install_commands`
  ([rocm.rs#L413-L426](rusty-stack/src/installers/components/rocm.rs#L413-L426))
  builds a single `PackageCommand { program: aur_helper, args: ["-S",
  "--needed", "--noconfirm", <pkgs>] }`. No `sudo` wrapper, no bare operation.
- The Arch branch in `installer.rs` (`"rocm" =>`)
  ([installer.rs#L3077-L3170](rusty-stack/src/installer.rs#L3077-L3170))
  builds one `yay -S [--needed] --noconfirm … <pkgs>` command, attaches
  `--sudo-flags=-A` + `SUDO_ASKPASS` for yay's internal `sudo pacman`, and runs
  it with `execute_native_command(&yay_cmd, None, …)` — `sudo_pw=None`
  explicitly so `yay` is never wrapped in `sudo -S` (line 3170, with comment
  that running yay as root is refused).
- No `sudo yay` (bare or otherwise) appears on any code path.

### A2. No-CUDA hard-prime intact — **MET**

- `installer.rs::execute_native_command`
  ([installer.rs#L2079-L2130](rusty-stack/src/installer.rs#L2079-L2130))
  detects pip-install invocations (`uv` / `*pip` / `*pip3` / args contain
  `pip`, AND args contain `install`) and, for each non-flag positional arg,
  calls `nvidia_blocklist::is_nvidia_cuda_runtime_package` and (for `http…`
  args) `is_cuda_wheel_url`, bailing on a hit.
- `-r/--requirement/-c/--constraint` filenames are skipped (so `cuda.txt` as a
  requirements file is not blocked) — correct.
- `nvidia_blocklist::is_nvidia_cuda_runtime_package`
  ([nvidia_blocklist.rs#L214-L230](rusty-stack/src/installers/common/nvidia_blocklist.rs#L214-L230))
  blocks the `nvidia*/cuda*/cudnn/cublas/cufft/…/nccl/tensorrt/pytorch-cuda/
  torch-cuda` prefixes plus any name containing `cuda`, while the prefix list
  ([NVIDIA_RUNTIME_PREFIXES#L189-L206](rusty-stack/src/installers/common/nvidia_blocklist.rs#L189-L206))
  deliberately excludes plain `torch`/`triton`, permitting them from the ROCm
  index.

## PART B — rocminfo-free GPU detection

### B1. Unified sysfs detector — **MET**

- `gpu.rs::detect_amd_gpus`
  ([gpu.rs#L430-L540](rusty-stack/src/gpu.rs#L430-L540))
  walks `/sys/class/drm/card*` (skips `cardN-*` outputs), canonicalizes +
  dedupes by path, keeps `vendor == 0x1002`, parses `class` and masks with
  `0xFFFF00`, accepting only `0x030000` (VGA) or `0x030200` (3D) — bridges
  (`0x0604`) / audio (`0x0403`) are rejected. Reads `device`,
  `mem_info_vram_total` (via `read_vram_bytes`), classifies with
  `device_is_integrated`. **rocminfo is not consulted anywhere** in the
  function.
- Live validation on the review box: `card1=0x744c`, `card2=0x747e`,
  `card3=0x164e`, all `class=0x030000`; `rocminfo` is NOT on PATH — detection
  works on a ROCm-free box.

### B2. dGPU enumeration — **MET**

- `gpu.rs::detect_discrete_amd_gpus`
  ([gpu.rs#L545-L552](rusty-stack/src/gpu.rs#L545-L552))
  filters `!is_integrated` and sorts by `pci_slot`.
- The iGPU `0x164e` (Raphael) is in `INTEGRATED_PCI_DEVICE_IDS`
  ([gpu.rs#L46](rusty-stack/src/gpu.rs#L46))
  so `is_integrated_by_pci_id` excludes it, while `0x744c`/`0x747e` are kept.
  Confirmed against the live box (the iGPU is dropped, both dGPUs survive).

### B3. PCI-ID → gfx matrix — **NOT MET (Critical: RDNA4 inverted)**

`DISCRETE_PCI_ID_TO_GFX`
([gpu.rs#L323-L370](rusty-stack/src/gpu.rs#L323-L370)).

- **RDNA2 / RDNA3 mappings are correct** (spot-checked against `pci.ids`):
  `0x744c`=Navi31→gfx1100 ✓, `0x747e`=Navi32→gfx1101 ✓, `0x73bf`=Navi21→gfx1030 ✓,
  `0x73df`=Navi22→gfx1031 ✓, `0x73ff`=Navi23→gfx1032 ✓, `0x743f`=Navi24→gfx1034 ✓,
  `0x7480`/`0x73f0`=Navi33→gfx1102 ✓.
- **RDNA4 mappings are INVERTED** (Critical):
  - `("0x7550", "gfx1200")` and `("0x7551", "gfx1200")` — `pci.ids` says
    `7550`/`7551` are **Navi 48** (RX 9070 / R9700). Authoritative ROCm spec:
    **Navi 48 = gfx1201**. The code says `gfx1200`. **WRONG.**
  - `("0x7590", "gfx1201")` — `pci.ids` says `7590` is **Navi 44** (RX 9060 XT).
    Authoritative ROCm spec: **Navi 44 = gfx1200**. The code says `gfx1201`.
    **WRONG.**

  Evidence (ROCm `gpu-arch-specs`): "Radeon RX 9070 XT … gfx1201", "Radeon RX
  9060 XT … gfx1200"; Tom's Hardware/WCCFTech: "Navi 44 GFX1200 & Navi 48
  GFX1201." The two RDNA4 dies are swapped.

  Impact: any RX 9070/9070 XT/9070 GRE owner (the flagship RDNA4 part) is
  assigned `gfx1200`, and any RX 9060 owner is assigned `gfx1201`. Downstream
  `HSA_OVERRIDE_GFX_VERSION` is consequently wrong (12.0.0 vs 12.0.1), and
  PyTorch-ROCm wheels keyed on the gfx target will mismatch. This violates the
  foundational requirement to "correctly identify … their gfx architectures."

### B4. Arch resolution returns Option, never gfx000 — **PARTIALLY MET**

- **gfx000 eradication: MET.** `pci_id_to_gfx`
  ([gpu.rs#L383-L389](rusty-stack/src/gpu.rs#L383-L389))
  and `gfx_from_marketing_name`
  ([gpu.rs#L395-L520](rusty-stack/src/gpu.rs#L395-L520))
  both return `Option`, `None` on unknown. The string `"gfx000"` does **not**
  appear anywhere in `gpu.rs`.
- **RDNA4 mapping correctness: NOT MET (Critical).** Same inversion as B3 in the
  marketing-name path:
  - `navi 48`/`9070 xt`/`9070 gre` → `gfx1200`
    ([gpu.rs#L398-L400](rusty-stack/src/gpu.rs#L398-L400),
    [#L478-L484](rusty-stack/src/gpu.rs#L478-L484))
    — should be `gfx1201`.
  - `navi 44`/`9060` → `gfx1201`
    ([gpu.rs#L401-L403](rusty-stack/src/gpu.rs#L401-L403),
    [#L485-L487](rusty-stack/src/gpu.rs#L485-L487))
    — should be `gfx1200`.

  The "generic Navi NN" patterns the claim asks for are present, but they encode
  the wrong RDNA4 die→gfx relationship.

### B5. Delegation + gfx000 eradication — **MET**

- `installer.rs::detect_gpu_arch`
  ([installer.rs#L5558-L5562](rusty-stack/src/installer.rs#L5558-L5562))
  returns `Option<String>` and delegates to `gpu::detect_discrete_amd_gpus()`.
- `detect_discrete_gpus`
  ([installer.rs#L5602-L5608](rusty-stack/src/installer.rs#L5602-L5608))
  and `detect_gpu_list` (L5586-L5600) likewise delegate.
- A repo-wide grep for `gfx000` finds only **rejection logic, comments, and one
  test** (`installer.rs:5557` comment; `component_status.rs:1206/1214` rejection;
  `env_validation.rs:189/197/200` rejection; `llama_cpp.rs:1485` test). No
  `gfx000` *fallback* anywhere.

  Note (Low, cosmetic): `detect_discrete_gpus`/`detect_gpu_list` doc comments
  still describe a "rocminfo → rocm-smi → lspci → sysfs" cascade, but the code
  uses sysfs only. Stale docs, not a behavior defect. `detect_gpu_list` still
  emits a legacy `"0"` device-mask default when empty (documented), which is not
  a gfx fallback.

## PART C — Managed Python environment

### C1. Version cap (≤3.13, prefer 3.12, reject 3.14) — **MET**

- `environment.rs::resolve_managed_python`
  ([environment.rs#L514-L596](rusty-stack/src/platform/environment.rs#L514-L596)):
  uv backend runs `uv python find 3.12`, else `uv python find ">=3.10,<3.14"`;
  python backend scans `python3.12, 3.11, 3.10, 3.13` via
  `check_python_version_cap`.
- `check_python_version_cap`
  ([environment.rs#L572-L614](rusty-stack/src/platform/environment.rs#L572-L614))
  parses `--version` and hard-rejects `major > 3 || (major == 3 && minor > 13)`
  — 3.14+ is refused, not deprioritized. The managed resolver does **not** use
  the legacy newest-first `discover_python_candidates`, so the "3.14 beats 3.12"
  prior bug is not inherited. No path selects system 3.14.

### C2. Global env creation — **MET**

- `create_global_env`
  ([environment.rs#L621-L678](rusty-stack/src/platform/environment.rs#L621-L678))
  materializes one env at `~/.mlstack/global` (`uv venv … --python <resolved>`
  or `<resolved> -m venv …`), returning `mlstack_global_python()` =
  `~/.mlstack/global/bin/python`
  ([environment.rs#L135-L137](rusty-stack/src/platform/environment.rs#L135-L137)).
- `resolve_canonical_python_bin`
  ([environment.rs#L301-L330](rusty-stack/src/platform/environment.rs#L301-L330))
  treats that path as authoritative (step 2, after only an explicit user
  override / named env).

### C3. Backend toggle — **MET**

- `config.rs::PythonBackend`
  ([config.rs#L7-L26](rusty-stack/src/config.rs#L7-L26)):
  `Uv`/`Python`, `Default` = `Uv` if `uv` on PATH else `Python`.
  `MLSTACK_PYTHON_BACKEND` env override applied in both `apply_from_value`
  (L160-167) and `default_with_paths` (L184-194). Persisted to config.json under
  `user_preferences.python_backend` (L106).

### C4. Shell-aware global prepend — **MET**

- `offer_global_prepend`
  ([environment.rs#L714-L800](rusty-stack/src/platform/environment.rs#L714-L800)):
  detects `$SHELL` (fish/zsh/bash→rc + snippet), prompts `[Y/n]` (default-Y) on
  a TTY, acts on no-TTY or `yes_default`, and appends ONE line tagged
  `# mlstack-global-python`. Marker-present → early `Ok(false)` (idempotent).
  When the user declines (`!act`) it returns before any write — the rc is not
  modified.

### C5. All stack ops route through the managed env — **PARTIALLY MET (Medium)**

- **Letter of the claim: MET.** No component installer hardcodes a bare
  `python3`/`pip`/`pip3` for an install op; all use `self.config.python_bin -m
  pip …` or `uv` (e.g. pytorch.rs L223-227, comfyui.rs L251-263, wandb.rs,
  vllm_multi.rs, megatron.rs, aiter.rs, migraphx_python.rs,
  bitsandbytes_multi.rs). The only bare `python3` strings are in generated
  launcher shims (textgen/comfyui), not install steps.
- **Spirit at risk: see D2.** The `python_bin` value that components consume is
  taken from `MLSTACK_PYTHON_BIN` in `.mlstack_env` (via
  `load_mlstack_env_exports`) or `resolve_python_bin`. In `run_installation`,
  `ensure_mlstack_env` writes `.mlstack_env` **before** the managed global venv
  is created, and the per-run `python_bin` prefers the persisted file value
  ([installer.rs#L144-L164](rusty-stack/src/installer.rs#L144-L164)).
  On a clean first install, `~/.mlstack/global` does not yet exist when
  `ensure_mlstack_env` runs (L67), so the file is stamped with a *discovered*
  interpreter; the global venv created later (L126) does not retroactively
  become the persisted `python_bin` for that run. Net effect: components can
  install into a discovered interpreter rather than the canonical
  `~/.mlstack/global` on first run. Components-as-written are correct; the
  ordering/precedence of `python_bin` resolution undermines "all ops route
  through the managed env."

## PART D — Wiring + zero-tolerance hygiene

### D1. permanent-env arm fail-loud + de-sudo + precise HSA — **PARTIALLY MET (High)**

The arm: `installer.rs` `"permanent-env" =>`
([installer.rs#L3001-L3063](rusty-stack/src/installer.rs#L3001-L3063)).

- **Fail-loud: MET.** Calls `gpu::detect_discrete_amd_gpus()` directly (L3013),
  `bail!`s when empty ("no AMD dGPU detected via sysfs", L3015), and `bail!`s
  when the primary dGPU's `gfx_arch` is `None` (L3021-3025).
- **De-sudo / no rocminfo: MET.** The arm executes only
  `build_mkdir_triton_dirs_command` and `build_rocm_version_detect_command`
  (the latter is `cat /opt/rocm/.info/version`
  ([permanent_env.rs#L277-L283](rusty-stack/src/installers/components/permanent_env.rs#L277-L283))).
  No `sudo rocminfo`. `build_rocminfo_gpu_detect_command` exists but is
  referenced only by a `#[cfg(test)]` test (L494), never by the arm.
- **Precise HSA / device derivation: NOT MET in the produced artifact.** The arm
  computes `hsa_override = GpuArchInfo::from_arch(&gpu_arch).hsa_override_gfx_version`
  (precise: gfx1101→11.0.1) and derives `discrete_list` from the detector, then
  stores them in `PermanentEnvConfig`. **But that config is never written.** The
  config's only consumers — `generate_env_file_content` and `required_env_vars`
  — are invoked only from `#[cfg(test)]` (permanent_env.rs `#[cfg(test)]` begins
  at L321; all `generate_env_file_content` call sites L341-531 are inside it).
  The `.mlstack_env` that is actually produced is written by
  `installer.rs::ensure_mlstack_env`
  ([installer.rs#L602-L742](rusty-stack/src/installer.rs#L602-L742)),
  which derives `HSA_OVERRIDE_GFX_VERSION` from the **coarse**
  `hsa_override_from_gpu_arch`
  ([installer.rs#L5688-L5707](rusty-stack/src/installer.rs#L5688-L5707))
  (`gfxMMNN`→`MM.0.0`, so gfx1101→**11.0.0**, with a `"11.0.0"` fallback). So the
  precise per-variant override the claim describes (gfx1101→11.0.1) never reaches
  the env file. `HIP_VISIBLE_DEVICES`/`PYTORCH_ROCM_DEVICE` in the written file
  do still come from the same sysfs detector (via `detect_gpu_list`/
  `detect_gpu_arch`), so that sub-part holds — but via the parallel path, not the
  arm's config.

  Additional concern (Medium): `ensure_mlstack_env` is **not** fail-loud — it
  falls back to `gfx1100` + `11.0.0` with only an eprintln warning when no GPU
  arch is detected. It runs at the top of every `run_installation`, independent
  of whether the permanent-env component succeeds, so a `gfx1100` env file can be
  written on a box where the permanent-env arm would bail.

### D2. Managed Python wired into env creation — **NOT MET (High)**

- The arm does call all four functions in order: `resolve_managed_python` →
  `create_global_env` → `write_activate_snippets` → `offer_global_prepend`
  ([installer.rs#L3034-L3038](rusty-stack/src/installer.rs#L3034-L3038)).
- **But the resolved `~/.mlstack/global/bin/python` is NOT the `python_bin` in
  `PermanentEnvConfig`.** `python_bin` is set to `py`
  ([installer.rs#L3040](rusty-stack/src/installer.rs#L3040)),
  which is the return of `resolve_managed_python` — the **bootstrap**
  interpreter used to *create* the venv (a system/uv interpreter), not the
  venv's own `python`. The actual global-python path returned by
  `create_global_env` is discarded (`create_global_env(&backend)?;`, return value
  unused, L3036).
- Compounding this, as noted in D1, `PermanentEnvConfig` is never written, so
  even the (wrong) `python_bin` is moot for the produced file. The file's
  `MLSTACK_PYTHON_BIN` is set independently by `ensure_mlstack_env` and is
  subject to the first-run ordering issue described in C5.

  The claim "the resolved `~/.mlstack/global/bin/python` is the `python_bin` in
  `PermanentEnvConfig`" is false as written.

### D3. Content-aware verification — **MET**

- `component_status.rs::env_file_has_permanent`
  ([component_status.rs#L1197-L1231](rusty-stack/src/component_status.rs#L1197-L1231)):
  after the marker check, parses `GPU_ARCH=`, returns `false` for `gfx000`, and
  returns `false` for any arch not starting with one of
  `gfx9/gfx10/gfx11/gfx12`. A `gfx000`/garbage-arch env can no longer be reported
  Verified.
- Caveat (consistent with D1): a `gfx1100` *fallback* env (written by
  `ensure_mlstack_env` on a GPU-less box) is structurally valid and would pass
  this check — the content-aware guard catches `gfx000`/invalid arches as
  specified, but not a plausible-but-wrong fallback arch.

### D4. No suppression — **MET**

- The new v0.3.1 modules carry **zero** `#[allow]`: `gpu.rs`, `environment.rs`,
  `config.rs`, `askpass.rs`, `permanent_env.rs`, `component_status.rs`,
  `uninstall.rs`, `rocm.rs`, `nvidia_blocklist.rs`.
- The dead rocminfo/rocm-smi/lspci cascade parse functions are **gone** (deleted,
  not suppressed) — a grep for `parse_rocminfo`/`parse_rocm_smi`/`parse_lspci`
  and similar finds nothing in `installer.rs`/`gpu.rs`.
- The remaining `#[allow]` attributes in `installer.rs` (L610/L867/L1720/L1962/
  L2378/L4943/L5719) are on pre-existing helpers with justification comments

## Overall Verdict

The post-merge hotfix (Part A) and the structural detection plumbing (B1, B2,
B5) are solid and verifiable from source, and the managed-Python primitives (C1–
C4) are correct in isolation. However, three findings block a clean pass:

1. **RDNA4 gfx mapping is inverted everywhere (Critical, B3/B4).** RX 9070 (Navi
   48) → must be `gfx1201`; RX 9060 (Navi 44) → must be `gfx1200`. The code has
   them swapped in all four tables and in the tests. This breaks the core
   promise of correct gfx identification for the entire RDNA4 generation.

2. **The permanent-env arm's detector-driven config is never written
   (High, D1/D2).** The precise per-variant HSA (`GpuArchInfo::from_arch`) and
   the managed-global `python_bin` are computed into a `PermanentEnvConfig` whose
   only writers are test-only. The real `.mlstack_env` is produced by the older
   `ensure_mlstack_env` path using the coarse HSA mapping and an independently
   resolved (and order-sensitive) `python_bin`. D2's specific claim is false;
   D1's "precise HSA" sub-claim is not realized in the artifact.

3. **Managed-env routing is order-fragile on first install (Medium, C5).** The
   global venv is created after `.mlstack_env` is stamped, and the per-run
   `python_bin` prefers the already-persisted (discovered) value, so first-run
   installs can land outside `~/.mlstack/global`.

Everything else (A1–A7, B1, B2, B5, C1–C4, D3, D4) is **MET** by source.
