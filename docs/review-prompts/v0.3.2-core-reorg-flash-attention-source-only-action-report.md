# v0.3.2 Core Reorg + Flash Attention Split Source-Only Action Report

Date: 2026-06-27

Scope: Rusty Stack source review for the Core category reorganization and Flash Attention backend split (`flash-attn-triton` / `flash-attn-ck`).

Method: source-only review. No LeIndex. No test output used as proof. Findings below come from reading local source files with `rg`, `sed`, and line-numbered file reads.

## Executive Summary

The Core category reorganization mostly landed: the `Maintenance` category exists in both category enums, TUI category membership is largely correct, Flash Attention is split in the component list, FA-CK is selectable and labeled experimental, and the false-positive detection root cause was mostly removed from the installed-status path.

However, the Flash Attention split is not complete enough to release. The biggest issue is that the new split component ids can install but cannot verify successfully through the normal installer completion path, because component verification only handles the canonical `"flash-attn"` id. That means a successful `flash-attn-triton` or `flash-attn-ck` build can still be reported as failed after install. There are also source-level drifts around legacy verification imports, `--no-deps` dependency guarantees, marker write semantics, registry tests, and planner alias handling.

Overall verdict: **NOT RELEASE-READY** until Critical and High findings are fixed and re-verified from source.

## Findings

### 1. Critical: Split Flash Attention ids have no component verification commands

Status: **NOT MET**

Severity: **Critical**

Primary files:

- `rusty-stack/src/component_status.rs`
- `rusty-stack/src/installer.rs`

Evidence:

```rust
// rusty-stack/src/component_status.rs
pub fn component_verification_commands(
    component_id: &str,
    python_candidates: &[String],
) -> Vec<VerificationCommand> {
    match component_id {
        ...
        "flash-attn" => vec![python_command(
            "Flash Attention",
            "flash-attn",
            &["flash_attn", "flash_attention_amd", "flash_attn_2"],
            python_candidates,
            "...",
        )],
        ...
        _ => Vec::new(),
    }
}
```

`component_verification_commands()` only matches `"flash-attn"`. It does not match `"flash-attn-triton"` or `"flash-attn-ck"`.

```rust
// rusty-stack/src/installer.rs
fn run_component_verification(
    component: &Component,
    python_candidates: &[String],
    sender: &Sender<InstallerEvent>,
    user_home: &str,
) -> VerificationOutcome {
    let steps = component_verification_commands(&component.id, python_candidates);
    ...
    let success = executed > 0 && failed == 0;
```

If the installed component id is `"flash-attn-triton"` or `"flash-attn-ck"`, `steps` is empty, `executed` remains `0`, and `success` is false. The installer then treats this as a failed final result even if the FA pip install succeeded.

Engineering logic:

The reorg introduced concrete installable ids. Any installable id must have a verification path if the installer requires post-install verification for final success. Otherwise, the application behavior contradicts the UI: the user can select and install a backend, but the app cannot mark that backend completed through its own success criteria.

Recommended fix:

Add explicit verification arms for `"flash-attn-triton"` and `"flash-attn-ck"` that verify:

1. `flash_attn` importability.
2. Expected backend marker value.
3. Optional functional symbol check for `flash_attn.flash_attn_func`.

Preferred pattern: create a helper to avoid three drift-prone inline snippets.

Patch sketch:

```rust
fn flash_attention_verification_command(
    label: &str,
    target_id: &str,
    expected_backend: Option<&str>,
    python_candidates: &[String],
) -> VerificationCommand {
    let marker_check = match expected_backend {

        r#"

    print("flash_attn_func missing")
    sys.exit(1)
{marker_check}
print("flash_attn OK")
"#
    );

    python_command(label, target_id, &["flash_attn"], python_candidates, &code)
}

// In component_verification_commands()
"flash-attn" => vec![flash_attention_verification_command(
    "Flash Attention",
```

Implementation note:

The exact internal FA symbol path may differ by package version. If `flash_attn.flash_attn_interface.flash_attn_func` is not stable for ROCm FA, use `import flash_attn` as the hard minimum and check for known public functions using a tolerant list. Do not keep accepting legacy `flash_attention_amd`.

### 2. High: Flash Attention verification still accepts legacy `flash_attention_amd`

Status: **PARTIALLY MET**

Severity: **High**

Primary file:

- `rusty-stack/src/component_status.rs`

Evidence:

Installed detection for canonical FA uses only current package names:

```rust
// rusty-stack/src/component_status.rs
"flash-attn" => python_any(python_candidates, &["flash_attn", "flash_attn_2"]),
```

Split detection is stricter:

```rust
"flash-attn-triton" => {
    python_any(python_candidates, &["flash_attn", "flash_attn_2"])
        && backend_marker_is("triton")
}
"flash-attn-ck" => {
    python_any(python_candidates, &["flash_attn", "flash_attn_2"])
        && backend_marker_is("ck")
}
```

But verification still accepts legacy module names:

```rust
"flash-attn" => vec![python_command(
    "Flash Attention",
    "flash-attn",
    &["flash_attn", "flash_attention_amd", "flash_attn_2"],
    python_candidates,
    "import importlib, sys;\nmodules=[('flash_attn','flash_attn.flash_attn_func'),('flash_attention_amd',None),('flash_attn_2',None)];\n...",
)],
```

Same legacy set also appears in enhanced/build verification commands.

Engineering logic:

The original false positive came from old Flash Attention AMD artifacts. The installed-status path no longer checks `flash_attn_amd*` directories, which is good. But a verification path that accepts `flash_attention_amd` can still bless legacy artifacts as "Flash Attention" even though the new install contract says both backends come from `ROCm/flash-attention` and install `flash_attn`.

This is a trust-boundary problem: detection and verification must agree on what "installed" means. If detection says no but verification says yes, users and automation get contradictory truth.

Recommended fix:

Remove `flash_attention_amd` from all active Flash Attention verification module lists and snippets.

Search targets:

```bash
rg -n "flash_attention_amd|flash_attn_2|flash_attn" rusty-stack/src/component_status.rs
```

Expected result after fix:

- `flash_attention_amd` does not appear in active verification logic.
- If `flash_attn_2` is retained as a compatibility import, document why. Prefer only `flash_attn` unless source evidence shows ROCm package exposes `flash_attn_2`.

Patch sketch:

```rust
// Before
&["flash_attn", "flash_attention_amd", "flash_attn_2"]

// After
&["flash_attn"]
```

Verification after fix:

- Source read: `rg -n "flash_attention_amd" rusty-stack/src/component_status.rs` should return no active verification references.
- Source read: detection and verification both depend on `flash_attn` importability for current FA.

### 3. High: `--no-deps` dependency guarantee is false for Flash Attention

Status: **PARTIALLY MET**

Severity: **High**

Primary files:

- `rusty-stack/src/installer.rs`
- `rusty-stack/src/installers/components/mod.rs`

Evidence:

Installer comment claims:

```rust
// rusty-stack/src/installer.rs
// --no-deps is safe + correct here: torch, einops, ninja, packaging and
// psutil are guaranteed present (pytorch + deepspeed run first via
// dependency ordering), so --no-deps scopes the install to flash_attn
// itself and can NEVER pull a CUDA torch to satisfy a torch requirement.
```

But dependency graph declares:

```rust
// rusty-stack/src/installers/components/mod.rs
"flash-attn" | "flash-attn-triton" | "flash-attn-ck" => &["pytorch", "rocm"],
```

There is no `deepspeed` dependency. Therefore, `einops`, `ninja`, `packaging`, and `psutil` are not guaranteed by dependency ordering.

Engineering logic:

`--no-deps` is the right direction for preventing CUDA torch resolution, but it creates a new obligation: every real build/runtime dependency must be installed explicitly before the package install. The source currently contains a safety claim that is not enforced by the dependency graph. That can yield a build that fails unpredictably depending on the user's environment.

Recommended fix:

Keep `--no-deps`, but explicitly install FA-safe build deps from a curated list before `pip install .`.

Suggested curated dependency step:

```rust
let fa_deps = vec![
    "-m".to_string(),
    "pip".to_string(),
    "install".to_string(),
    "--break-system-packages".to_string(),
    "einops".to_string(),
    "ninja".to_string(),
    "packaging".to_string(),
    "psutil".to_string(),
];
execute_native_command(
    &NativeCommand::Shell {
        program: resolve_python_bin(),
        args: fa_deps,
        env: vec![],
        working_dir: None,
    },
    None,
    sender,
    &component.name,
)?;
```

Risk judgment:

- `einops`, `ninja`, `packaging`, and `psutil` are not CUDA runtime packages.
- The universal pip chokepoint still blocks explicit `nvidia-*`, `cuda*`, CUDA wheel URLs, etc.
- The actual FA package install should remain `--no-deps`.

Alternative fix:

Add dependency declarations that force an existing component to supply these packages. This is weaker and less direct because `deepspeed` is semantically unrelated to installing FA. Prefer a local explicit FA prerequisite step.

Verification after fix:

- Source read: FA arm installs explicit safe deps before `--no-deps`.
- Source read: no dependency step can install `torch`, `triton`, `xformers`, `flash-attn`, `nvidia-*`, or CUDA wheel URLs.
- Optional runtime: run pip command construction tests or integration tests with mocked command executor.

### 4. Medium: Backend marker write is warning-only, but marker is part of detection contract

Status: **PARTIALLY MET**

Severity: **Medium**

Primary files:

- `rusty-stack/src/installer.rs`
- `rusty-stack/src/component_status.rs`

Evidence:

Marker write after successful FA install:

```rust
let marker = PathBuf::from(&target_dir).join(".backend");
if let Err(err) = std::fs::write(&marker, backend_name) {
    let _ = sender.send(InstallerEvent::Log(
        format!(
            "[native] {} - warning: failed to write backend marker {:?}: {}",
            component.name, marker, err
        ),
        true,
    ));
}
```

Detection requires marker:

```rust
"flash-attn-triton" => {
    python_any(python_candidates, &["flash_attn", "flash_attn_2"])
        && backend_marker_is("triton")
}
"flash-attn-ck" => {
    python_any(python_candidates, &["flash_attn", "flash_attn_2"])
        && backend_marker_is("ck")
}
```

Engineering logic:

The marker is not informational. It is required for honest backend detection and mutual exclusivity. If writing it fails, the installer should fail loudly because the installed package is now in an untrackable state. Warning-only behavior creates exactly the kind of divergence the reorg was meant to eliminate: package installed, detection false, UI confusing.

Recommended fix:

Make marker write fatal.

Patch sketch:

```rust
let marker = PathBuf::from(&target_dir).join(".backend");
std::fs::write(&marker, backend_name)
    .with_context(|| format!("failed to write Flash Attention backend marker {}", marker.display()))?;
```

Optionally fsync parent if you want stronger durability, but normal `write` error propagation is enough for this repair.

Verification after fix:

- Source read: FA arm returns `Err` on marker write failure.
- Source read: marker write happens only after successful pip install.

### 6. Medium: Orchestrator planner does not know split FA ids

Severity: **Medium**

Evidence:

Derived dependencies only name canonical FA and only depend on PyTorch:

Recommended fix:

Update planner matching to include all FA ids and keep dependency semantics consistent with native deps.

```rust
| "flash-attn-ck"
```

### 7. Medium: Registry sealing and pip-package ownership do not include split backend ids

Status: **PARTIALLY MET**

Severity: **Medium**

Primary files:

- `rusty-stack/src/core/registry.rs`
- `rusty-stack/src/installer.rs`

Evidence:

Sealed install-once ids:

```rust
pub const SEALED_INSTALL_ONCE_IDS: &[&str] = &[
    "aiter",
    "flash-attn",
    "flash_attention",
    "flash_attention_amd",
    "rccl",
    "migraphx",
    "bitsandbytes",
];
```

Split ids omitted.

Owned pip packages:

```rust
fn component_pip_packages(id: &str) -> Vec<String> {
    match id {
        ...
        "flash-attn" | "flash_attention" => {
            vec!["flash-attn", "flash_attn", "flash_attention_amd"]
        }
        ...
    }
}
```

Split ids omitted.

Engineering logic:

This area needs product judgment. The new design says Triton and CK are mutually exclusive and the last-installed backend should become active. That conflicts with a broad "sealed install-once" rule if applied blindly to split ids. Still, registry metadata should not be empty or misleading. At minimum, if split backend installs are recorded, their owned pip packages should be populated. For sealing, decide explicitly:

- If FA must be protected from accidental overwrite, seal both split ids and require an intentional backend switch operation.
- If backend switching is allowed by selecting the other backend, do not seal split ids, but document the exception and make marker rewrite authoritative.

Current source does neither explicitly. It omits split ids from sealing and from owned packages.

Recommended fix:

At minimum:

```rust
"flash-attn" | "flash-attn-triton" | "flash-attn-ck" | "flash_attention" => {
    vec!["flash-attn", "flash_attn"]
}
```

Remove `flash_attention_amd` from owned packages if legacy support is being retired. Keep it only in uninstall/purge if cleanup of old artifacts is desired.

For sealing, choose one:

Option A, backend switching allowed:

```rust
// Leave split ids unsealed, but add a comment:
// Flash Attention split ids are intentionally not sealed because installing
// one backend over the other is the supported mutual-exclusion switch.
```

Option B, backend switching requires explicit unseal:

```rust
pub const SEALED_INSTALL_ONCE_IDS: &[&str] = &[
    "aiter",
    "flash-attn",
    "flash-attn-triton",
    "flash-attn-ck",
    ...
];
```

Recommended engineering judgment:

Use Option A only if the product wants backend switching from the TUI. Then ensure UI copy says installing one backend replaces the other, and marker write failure is fatal. Use Option B if "Flash Attention is key/core and must never be overridden accidentally" is interpreted strictly.

Verification after fix:

- Source read: split ids are intentionally handled in registry metadata.
- Source read: comments explain backend-switch policy.
